Implementation plan · draft 1 · 2026-11-13

IR Transceiver Utility

A Rust + Kirigami desktop app that talks directly to the ELK Smart USB-C IR blaster (045c:0132). It can learn and capture IR codes, show them as binary, hex, decimal or Base64, save them to a library and transmit them again. This plan covers what the dongle actually does, mockups of every screen, the architecture, and a test-first build order.

1. What the dongle really is

It is not a USB serial device.

The 045c:0132 exposes one interface with two vendor-specific bulk endpoints (one IN, one OUT). There is no /dev/ttyACM* and no serial stream. The app has to claim interface 0 and do raw bulk transfers in user space, the same way the reference driver elksmart-comm does it with libusb.

The dongle also never sends anything on its own. It only replies to commands. A learn command arms the receiver, and the dongle answers once with the next IR signal it sees. The "always reading" capture mode below therefore re-arms learn in a loop and logs every byte that comes back from the IN endpoint.

Command set

BytesMeaning
FC FC FC FCIdentify. The reply picks plain or Huffman protocol.
FE FE FE FELearn. The reply is FE FE FE FE + u16 BE length + IR data.
FD FD FD FDStop, sent after learning.
FF FF FF FFTransmit header, then frequency, length and payload.

Wire details to implement

  • Learned data: 1 byte = 16 µs; each FF adds 4080 µs. The bytes alternate on/off.
  • Transmit values pass through mangle() (bit-reverse, then invert).
  • OUT chunks are at most 62 bytes, plus a checksum byte on full chunks, with a 2 ms pause between chunks.
  • Identify reply FC..FC 70 01 or FA FA FA FA means plain protocol. FC..FC 02 AA means Huffman.

Known quirks of the 0132

  • Other reports say the 0132 sends an extra FF FF FF FF before the learn reply. Your unit does not (fixture 1794596116): the reply starts directly with FE FE FE FE. The parser accepts both. Continuation chunks can also start with FF bytes, which are long gaps in the data, so an acknowledgement can only be recognised before the header.
  • Measured on your unit: IN data arrives as 63-byte transfers about 100 ms apart, so a 216-byte code takes about 0.3 s. The announced length matched the received bytes in all 3 captures.
  • A learn captures the whole button hold, NEC repeat frames included. One press gave 5 repeats (216 B) and a shorter press gave 3 (158 B). Send should offer to cut a code down to its first frame.
  • Sending FD FD FD FD and then FE FE FE FE straight away re-arms learn reliably, so the capture loop works.
  • Marks are measured about 50 us long and spaces about 50 us short (608/512 instead of 560/560 for NEC). Protocol guessing needs tolerances.
  • After a cancelled learn, the dongle ignores all commands until it receives an IR signal. According to elksmart-comm, libusb_reset_device() does not clear this. The ways known to work are pressing any remote button or unplugging the dongle. A power-cycle of the port from software has not been tested yet and needs a spike in P4.
  • The announced length doesn't always match the bytes actually received. Reads need a timeout rather than an exact byte count.

Things to check on your machine (phase 0)

  • Confirmed on your machine: 1 interface, class 0xFF (vendor) with subclass 0xF0, bulk OUT 0x02 and bulk IN 0x82, 64-byte packets, Full Speed, serial 030820250001.
  • udev access confirmed: /etc/udev/rules.d/70-elksmart.rules with TAG+="uaccess" gives the logged-in user an rw ACL on the USB node.
  • The interface string is "iAP Interface". No kernel driver binds to it, because the class is vendor-specific.
  • Make sure no kernel driver (cdc_acm, or anything LIRC-related) has claimed interface 0. LIRC is not needed for this app and may be in the way.
  • Capture a few reference dumps with elksmart-comm to use as test fixtures.

3. Architecture

A Cargo workspace splits the work into crates. Everything that can be tested without hardware or Qt lives in pure Rust crates. Only the last crate knows about Qt.

CrateJobDepends on
ir-codecTurns bytes into hex, binary, decimal and Base64 strings and back. The parsers are lenient: they accept separators and 0x/0b prefixes and report the position of any error.base64 0.23.1
elk-protoCommands, mangle, checksum, identify parsing, learn reply parsing (including skipping the FF ack), plain pulse decoding and encoding, chunking, and the NEC builder. No I/O.none
ir-transporttrait Transport { write, read(timeout), reset }, plus a nusb implementation, device discovery and hotplug. A scripted mock replays recorded dumps.nusb 0.2.9 (or rusb 0.9.4)
ir-sessionThe state machine on a worker thread (below). It owns the transport, emits typed events and keeps the bounded capture buffer.above, thiserror 2.0.21

The build follows KDE's "Setup with Rust" tutorial: CMake + ECM checks for Kirigami and QQC2DesktopStyle, drives Cargo, and installs the binary and the .desktop file. The tutorial pins cxx-qt 0.8.1, while 0.10.0 is current. Phase 1 confirms that the tutorial's setup still works on 0.10.

4. Session state machine

All USB I/O runs on one worker thread. The UI sends Commands over a channel. The worker posts Events back to the Qt thread through CxxQtThread::queue, so the GUI never blocks on USB.

stateDiagram-v2
  [*] --> Disconnected
  Disconnected --> Identifying: device found / Connect
  Identifying --> Ready: reply plain or huffman
  Identifying --> Recovering: 4 timeouts
  Ready --> Learning: Learn once
  Ready --> Capturing: Start capture
  Ready --> Transmitting: Send
  Transmitting --> Ready: all chunks written
  Learning --> Ready: frame complete / timeout
  Capturing --> Capturing: frame complete, re-arm learn
  Capturing --> Recovering: Stop while armed
  Learning --> Recovering: cancelled
  Recovering --> Identifying: any IR frame received
  Recovering --> Disconnected: user replugs
  Ready --> Disconnected: unplugged
  Capturing --> Disconnected: unplugged

Capture mode in detail. The worker sends FE FE FE FE and then reads in a loop with a 100 ms timeout. Every IN transfer is logged as its own row with a timestamp, including the ack, which keeps the "see all data" goal. Learn replies are reassembled from the announced length plus a quiet-time timeout. A complete frame is decoded into pulses, and learn is re-armed straight away. A frame that times out short is kept and marked short.

7. Resource guards

  • At startup, read MemAvailable from /proc/meminfo. The capture buffer budget defaults to the smaller of 64 MiB and 5 % of available memory, and can be changed in settings.
  • The capture buffer is a ring buffer with a fixed byte budget. When it is full, the oldest frames are dropped, a counter shows how many, and auto-export to file is offered.
  • Reads use fixed 64-byte buffers and learn reassembly is capped at 64 KiB per frame, so a misbehaving dongle can't grow memory without limit.
  • The bridge batches UI updates, so a flood of frames can't block the Qt event loop.
  • Development builds run under systemd-run --user --scope -p MemoryMax=… so an OOM stays contained.
